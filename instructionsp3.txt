1 Description
This assignment is intended to familiarize you with the HTTP protocol. HTTP is (arguably) the
most important application-level protocol on the Internet today: the Web runs on HTTP, and an
enormous number of other applications and APIs (streaming video, mobile apps, social-network and

Your goal in this assignment is to implement a web crawler that gathers data from a fake social

http://sprinter2.cs.vt.edu/fakebook/
2 What is a Web Crawler?
A web crawler (sometimes known as a robot, a spider, or a screen scraper) is a piece of software that
automatically gathers and traverses documents on the web. For example, suppose you have a crawler
and you tell it to start at www.wikipedia.org. The software will first download the Wikipedia
homepage, then parse the HTML and locate all hyperlinks (i.e., anchor tags) embedded in the page.
The crawler then downloads all the HTML pages specified by the URLs on the homepage and parses
them looking for more hyperlinks. This process continues until all of the pages on Wikipedia are
downloaded and parsed.
Web crawlers are a fundamental component of today’s web. For example, Googlebot is Google’s
web crawler: it constantly scours the web, downloading pages in search of new and updated content,
and this data forms the backbone of Google’s search engine.

7 Implementation Details and Hints
Your crawler must implement HTTP/1.1 (not 0.9 or 1.0). This means that there are cer-
tain HTTP headers, like Host, that you must include in your requests (they are required in
all HTTP/1.1 requests); use Host: sprinter2.cs.vt.edu. We encourage you to implement
Connection: keep-alive (persistent connections) to improve your crawler’s performance and
lighten the load on our server, but this is not required, and it is tricky to get right. We also
encourage you to implement Accept-Encoding: gzip (compressed HTTP responses), since this
will also improve performance for everyone, but this is also not required. (If you request gzip, a
response may be both compressed and chunked: reassemble the chunks first, then decompress.) If
you want to get fancy, you can speed up your crawler using multithreading or multiprocessing, but
this is not required either — and please keep it to at most 8 simultaneous connections, since
the server is shared by the whole class (see 503 below).

One of the key differences between HTTP/1.0 and HTTP/1.1 is that the latter supports chunked
transfer encoding. HTTP/1.1 servers may break up a large response into chunks, and it is the
client’s responsibility to reconstruct the data by combining the chunks. Our server sends most
pages chunked, so your client must be able to reconstruct them. Responses that are not chunked
carry a Content-Length header. To aid in debugging, you might consider using HTTP/1.0 for your
initial implementation; once you have a working 1.0 implementation, you can switch to 1.1 and add
support for chunked responses.
To build a successful web crawler, you will need to handle several different aspects of the HTTP
protocol:
• HTTP GET — necessary for downloading HTML pages.
• HTTP POST — you will need to implement HTTP POST so that your code can log in to
Fakebook. As shown above, you will pass a username and password to your crawler on the
command line. The crawler will then use these values as parameters in an HTTP POST in
order to log in to Fakebook.
• Cookie Management — Fakebook uses cookies to track logged-in clients. If your crawler
successfully logs in to Fakebook using an HTTP POST, Fakebook will return a session cookie
to your crawler. Your crawler should store this cookie and submit it along with each HTTP
GET request as it crawls Fakebook. The server may send new or updated cookies in any
response; keep your cookie store up to date. If your crawler fails to handle cookies properly, it
will not be able to crawl Fakebook successfully.
In addition to crawling Fakebook, your web crawler must correctly handle HTTP status codes.
You need to handle 200 OK, since that means everything is okay. Your code must also handle:
• 301 Moved Permanently and 302 Found — HTTP redirects. Your crawler should try the
request again using the new URL given by the server in the Location header. (The Location
may be an absolute URL or a path; handle both.)
• 403 Forbidden and 404 Not Found — our web server may return these codes to trip up
your crawler. In this case, your crawler should abandon the URL that generated the error
code.
• 500 Internal Server Error — our web server will randomly return this error code to your
crawler. In this case, your crawler should retry the request for that URL until the request is
successful.
• 503 Service Unavailable — the server returns this if a single client sends requests too
aggressively. Back off briefly, then retry the URL (a well-behaved crawler should never see it).
I highly recommend the HTTP Made Really Easy tutorial as a starting place for learning about
the HTTP protocol, along with RFC 9112 (HTTP/1.1 message syntax) for details such as chunked
encoding. The developer tools built into Chrome and Firefox are both excellent for inspecting
HTTP requests and responses. In addition to HTTP-specific issues, there are a few key things that
all web crawlers must do in order to function:
• Track the Frontier: As your crawler traverses Fakebook it will observe many URLs.
Typically, these uncrawled URLs are stored in a queue, stack, or list until the crawler is ready

to visit them. These uncrawled URLs are known as the frontier.
• Watch Out for Loops: Your crawler needs to keep track of where it has been, i.e., the
URLs that it has already crawled. It isn’t efficient to revisit the same pages over and over
again. If your crawler does not keep track of where it has been, it will almost certainly enter
an infinite loop. For example, if users A and B are friends on Fakebook, then A’s page links
to B, and B’s page links to A. Unless the crawler is smart, it will ping-pong back and forth:
A→B, B→A, A→B, . . .
• Only Crawl the Target Domain: Web pages may include links that point to arbitrary
domains (e.g., a link on google.com that points to cnn.com). Your crawler should only traverse
URLs that point to pages on sprinter2.cs.vt.edu. For example, it would be valid to
crawl http://sprinter2.cs.vt.edu/fakebook/018912/, but it would not be valid to crawl
http://www.facebook.com/018912/. Your code should check that each URL has a valid
domain (i.e., the domain is sprinter2.cs.vt.edu) before you attempt to visit it.
